## エグゼクティブサマリー

7領域の専門家診断をコードに照合した結論は明快です。**このプロジェクトの核（物理・操作・展開の設計思想）はすでに商用級の素地を持つが、それを「最高の騎乗体験」へ昇華させる3層——馬群AIの空間認識、ブロードキャスト演出、長期キャリア——が決定的に欠落しており、ビジュアルは2世代遅れている。**

重要なのは、7人全員が**それぞれ独立に同じ結論**へ到達した点です。すなわち「この領域はWeb/Three.jsで到達可能、ネイティブ移行は不要かつ逆効果」。唯一の例外が(a)骨格忠実な馬モデル、(b)抑揚のある実況音声——この2つだけが配布形態（単一HTML / アーティファクト）と正面衝突する真のWeb天井です。

そして査読が突きつけた**最も重い是正**は、「何を作るか」は優秀でも「いつ終わるか・本当に60FPSで動くか」が楽観的だった点です。本最終版は次の4つを構造的に組み込みました。

1. **60FPSは「達成項目」ではなく全Phase貫通の制約**である。これを支える**レンダリング予算オーケストレーター**をPhase1の独立L級必須土台へ格上げ。受け入れ基準を「最低端末ティア(中位Android)で30FPS下限 / iPhone15で60FPS」と二段化。
2. **物理再バランスは「収束保証のない多変数最適化」**である。L→XLへ格上げし独立トラック化。前提となる**ロスモデル拡張(`groundLoss=f(κ)`)をPhase2へ前倒し**、`balance_check.js`の**多目的グリッドサーチ自動化**を義務化。
3. **Phase3は事実上もう1本のプロジェクト**である。`3a=コース現実化トラック(r128のまま完遂)`と`3b=ビジュアル刷新トラック(r16x移行→アセット→ポストFX、厳格直列)`に分割。収録TTS/空間オーディオはPhase3から外しバックログへ退避。
4. **既存の判断ループ(`computeDesired`/`buildAdvice`/`computePaceForecast`)の磨き込み**——魂の核——をPhase1先頭に**新規物理ゼロの最大ROI施策**として昇格。新システムの積み増しより前に「判断が報われる密度」を底上げする。

### 最重要技術判断 ──【エンジン戦略】

**推奨: Three.js を当面 r128 据え置き、Phase3b で r16x系 + WebGL2 へ計画的アップグレード。WebGPU・ネイティブ移行(Unity/Unreal)はいずれも非推奨。**

| 選択肢 | 判断 | 根拠 |
|---|---|---|
| **r128 据え置き → r16x(Phase3b)** | ✅ **採用** | Phase1-2の価値(AI/カメラ/実況/影/IBL)は全てr128で実装可能。ポストプロセス(DoF/モーションブラー/Bloom)とスキンドメッシュ+Dracoが本格化するPhase3bで、examples/jsmモジュール群とカラーマネジメント刷新の恩恵が損益分岐を超える。**移行は単独で完了・検証してからアセット/ポストFXへ着手する厳格直列制約を課す**(査読: マテリアル全面再調整中に新規アセット色合わせは最悪の同時作業)。 |
| WebGPU | ❌ 却下 | 2026時点でもモバイルSafariのWebGPU対応が不安定。「スマホで動く」という事業の生命線を賭けられない。 |
| ネイティブ移行(Unity/Unreal) | ❌ 却下 | (1)「単一HTML/ブラウザで即遊べる・アーティファクト配布」が**最大の武器**でこれを捨てる。(2)物理/操作/カメラ/実況/AIの設計資産が全てJS実装に集約され移植コストが甚大。(3)絵作りの大半(影・IBL・Bloom・DoFのイベント限定発動)はWebで到達可能。理想を本気で狙うなら**別プロダクト**として判断すべき領域。 |

### アセット総量・対応端末の数値規約（査読: 上限が無く歯止めにならない / 対応マトリクス欠落）

定性的警告を数値ゲートへ昇格します。

- **HTML総量上限**: アーティファクト版 **≤2MB**(base64同梱の合計上限) / ローカル・サイト版は外部参照で実質無制限(ただし初回ロード体感のため初期同梱≤3MB目標)。スキンドメッシュ/収録音声は**この上限を満たす場合のみ同梱可**、超えるなら外部fetch(サイト配布)必須。
- **対応端末マトリクス(要Phase1事前検証)**: 基準=iPhone15(iOS Safari)。下限=中位Android(Chrome)。検証必須項目=①`EXT_disjoint_timer_query(_webgl2)`のモバイルSafari可否(=予算オーケストレーターの計測手段の可否。**無ければCPUフレーム時間にフォールバック**)、②同時テクスチャ数/MSAA上限、③WebAudio自動再生制限差、④Web Speech日本語音声の端末差(`CLAUDE.md §6`が苦労する領域)、⑤**アーティファクトでThree.js r128のCDN外部fetchが許可されるか自体**(現状CDN参照がアーティファクトで動くかが前提リスク)。

### 本質的緊張への正直な回答 ──「単一HTML × モバイル × 60FPS × PS4級ビジュアル」は同時成立するか

**結論: 「Switch発売タイトル相当」は同時成立する。「PS4世代・全部盛り常時」は成立しない。**

- **到達可能(Switch級)**: リアルタイム影(PCFソフト)・IBL/PBR・Bloom・GPU Instancing観客・動的解像度/LOD。縦画面スマホで見る分には十分Switch級。
- **イベント限定で可(PS4級の瞬間)**: DoF・モーションブラーは常時ONでは60FPS不可。**直線・スロー・ゴール前に限定発動**。発動時は予算オーケストレーターが**事前に解像度を1〜2段下げてバジェットを「予算先払い」**(査読fix)。スロー演出中は表示fps要求が下がる特性を活かし、**ゴール前接戦の鼻先ズームのみブラー無し・DoF弱め**に留める。
- **真のWeb天井(2つだけ)**: ①骨格忠実なスキンドメッシュ馬、②抑揚のある実況音声。配布形態の確定が技術判断の前提。

### 配布形態の戦略的分岐（全Phaseの前提・査読で事業判断として明文化）

キャリア永続化・音声素材・馬モデルアセットの全てがここに依存します。**Phase1冒頭で公式確定・文書化すべき最重要のプロダクション判断**であり、Phase1の必須受け入れゲートに昇格します。

- **一次（正規版）= ローカル/自社サイト配布の単一HTML**(localStorage可・外部アセット遅延fetch可)→ **フルキャリア・収録音声・GLTF外部参照が生きる**。本作の最大の差別化(育成ループ)はここでのみ完全体験。
- **二次（体験版）= claude.aiアーティファクト**(localStorage禁止・外部fetch不可)→ Save抽象レイヤでメモリフォールバック＆セーブ不可バナー。**単発レース内で完結する手応え(進路さばき・実況・写真判定)は全部入りを保証**するが、育成ループ不在は体験版として割り切る(査読minor: 中核価値がアーティファクトでは届かない事業判断を明記)。

この分岐を `Save.get/set/clear` 抽象1枚で吸収すれば同一コードベースで両対応でき大改修は不要です。

### 横断的優先順位の哲学（Phase配分の背骨）

> **本作の差別化は「ビジュアル」ではなく「ジョッキーの判断が報われるループ」にある。** ゆえにPhase1は「最も少ない工数で、Gallop Racer的な"判断ゲーム"の手応えを最速で立ち上げる」ものに集中する。査読(Gallop Racer純粋性)の是正を受け、Phase1は**「魂のコア(必須)」と「絵の格上げ(従)」に二分**し、後者は魂コアが実機で「能力下位馬を腕で覆せた」と確認できてから着手するゲートを設ける。**重いビジュアル(骨格モデル・東京府中再現・フルポスト)は核体験の骨格が立ったPhase2-3へ。**

ビジュアル向上が核体験を**損なってはならない**という絶対原則を、Phase配分そのものに織り込んでいます。

## エンジン横断の鉄則（全Phaseで遵守）── `CLAUDE.md §3` 追記想定

7領域の提案を貫く共通制約を、開発憲法へ追記すべき形で明文化します。

1. **物理の縦は凍結資産。** 速度・スタミナ式(`drain`/`topSpeed`/`floor`、`CLAUDE.md §3`)は安易に触らない。AI高度化は**横移動と相互作用のみ拡張**し、変更のたびに `node sims/balance_check.js` を回す。
2. **engine.js の同期は義務。** 本体のAIロジックを変えたら `sims/engine.js` に必ず移植し回帰を維持する。**現状TRK_R/TRK_SL/curveAtが本体とengine.js(line 9-10)で二重定義**されている問題は、Phase2のコース定義一元化で根治する。**根治前(Phase1)は本体↔engine.jsの差分レビューを全AI/物理変更の完了条件とする**(下記鉄則6・Phase1リスク節参照)。
3. **アセットは合成・手続き生成を維持。** 単一HTML肥大を避ける。例外はPhase3bのスキンドメッシュ(Draco base64)と収録音声のみで、いずれも**HTML総量規約(≤2MB/アーティファクト)と配布形態確定後に投資判断**。
4. **±15%思想は不可侵。** 固有/調子/距離適性/騎手スキル補正の合算が「腕で覆せる」範囲(各≤10-15%・合算クランプ)を超えない。**騎手スキルは馬能力数値(topSpeed/drain)に乗算せず、騎乗操作の有効性(出遅れ幅・composure回復率・進路変更レート・ムチ効果)に作用する独立軸として実装**(査読minor: 不利側合算下限が「腕で覆せない」水準に達する数理リスクを封じる)。AIに個性を与えても能力数値は動かさない(行動傾向のみ)。
5. **判定は残り距離ベースで書く。** `straightDist=DIST-400`(engine.js line 42・本体同構造)等の汎用仮定は東京直線525.9m移行で破綻するため、新規コードは `Course.homeStraightStart` からの残距離で記述する。
6. **【新設・査読blocker】全コミット前の4ゲート必須化。** `CLAUDE.md §8` のワークフローを改修プロセスへ完全統合する。
   - `node sims/balance_check.js`(物理・固有・距離変更時／スタミナ系は `node sims/stamina_tune.js` も)
   - `node --check`(インライン`<script>`抽出構文検証。**構文エラー1つで全画面白画面落ち**)
   - **非日本語CJK混入grep**(過去にハングル1文字混入事故あり)
   - 実ブラウザ実機プレイ確認(Playwright MCP推奨・スクショ＋consoleエラー)

## フレームバジェット（査読missingItem: 定量目標が無い）

`60FPS`の裏付けとして1フレーム16.6msの内訳目標を定義します。**Phase1の計測HUDで内訳プロファイラを必須化**し、各施策の工数見積もりの根拠とします。

| 区分 | 目標(iPhone15) | 計測点 |
|---|---|---|
| `stepRace`物理(AI/馬群/相互作用) | ≤3.0ms | CPU |
| `drawTrack`描画(メッシュ/脚アニメ/砂煙/影) | ≤7.0ms | GPU(timer query or 推定) |
| ポストFX(Composer/Bloom、発動時DoF/ブラー) | ≤3.5ms(常時) / イベント時は予算先払いで確保 | GPU |
| DOM HUD更新(順位/速度計/実況帯/インジケータ) | ≤1.5ms | CPU |
| 予備/GC | ≤1.6ms | — |

> 中位Android下限ティアでは同内訳を**33.3ms(30FPS)**に再配分。予算超過時はオーケストレーターが解像度→影→観客密度→ポストFXの順で自動段階低下。

## Phase 1 ──「判断ゲームの手応え」と「絵の格上げ」を最速で立てる

### ゴール

**「新人騎手として、空いた進路を読んで人気薄を駆り、実況に名を呼ばれながら格上の馬を差し切り、その戦績がローカル保存される」——単発キャリアループが既存資産だけで成立する。** 既存の判断ループ(折り合い・仕掛け・講評)が「判断中に見える」形へ磨かれ、密度が上がる。ビジュアルは接地影とIBLで「試作品感」を脱し、一人称ジョッキー視点で「乗っている」没入が生まれる。これだけで商用体験版として配布可能。

## 「最高の騎乗」を最も押し上げる ── Killer機能トップ5

7領域のkillerFeaturesを統合し、Gallop Racerの「最高の騎乗で能力差を覆した」達成感への寄与度で序列化します。**上位3つはすべてPhase1-2のthreejs-native＝最高のROI**です。

### 1位: 空き進路探索＋包まれ/被せの相互作用（⑥ / Phase1-2 / L）
**内で詰まり脚は余っているのに出せない焦り → 外が空いた一瞬を突いて抜け出す快感。** Gallop Racerの「最高の馬群さばき」を再現し、能力で劣る馬でも進路一つで勝てる＝絶対思想「腕で覆す」に最も直結する**核中の核**。これ無しに本作は「競馬風ゲーム」に留まる。**被せは必ず予兆HUDで先読み回避でき、運ゲーにしない。**

### 2位: 真の一人称ジョッキー視点 ＋ 鼻先フリーズフレーム写真判定（③⑤ / Phase1で土台→Phase2で完成 / L）
ストライド連動の上下動と速度FOVで「馬を見る」から「**私がこの馬に乗っている**」へ転換(Phase1)。接戦のゴールでサイドラインカメラに切り替わり、ラックフォーカス＋寄りで3D馬をフリーズフレーム、シャッターが切れる(写真判定はP1で暫定サイド寄せ→P2で完成の二段)。「鼻差で能力差を覆した」という設計の文字通りの**クライマックス**であり、現状が2Dフラッシュなので感情的ROIが最大。

### 3位: ペース因果エンジン ＋ 動的実況 ＋ 騎乗講評（⑦⑧⑩ / Phase1 / M）
逃げ馬の数とハナ争いから**本物のハイ/スロー**が抽選でなく因果で生成され(drain式は不変・commitDist/cruiseGain範囲に厳密に閉じる)、それを読んで位置取りと仕掛けを決める。当たれば差し切れる。そして「大外から〇〇が一気だ！」と**自分の騎乗が言葉になって返り**、講評が「読み通りに差せた/大外を回した距離ロス」を**採点**して次の上達動機を燃やす。「読みが報われた」達成感を物理・言語・採点の三層で確定させる。

### 4位: 育てた騎手で前は勝てなかった馬を勝たせる成長実感（⑩ / Phase1-2 / M）
スタート/折り合い/さばき/追いの4補正(各≤10%・**馬能力に乗算せず操作有効性に作用する独立軸**)と、人気薄を選んで格上を勝つ騎乗依頼ループ。**騎乗貢献度スコア(期待着順vs実着順)**で「腕が上がったから覆せた」をGallop Racer的に数値で確定。Web/単一HTMLで100%到達可能、最も確実な投資。

### 5位: ゴール前の坂を物理化した「坂で止まる馬を差し切る」体験（④ / Phase3a / M+XL再バランス）
東京の最も象徴的なジョッキー判断。坂下で脚を残すか、坂を力で押し上げるか。**東京府中を走っている実感**の決定打。ただし物理再バランス(XL・収束機械化)とセットの破壊的変更ゆえPhase3aに正しく配置。
